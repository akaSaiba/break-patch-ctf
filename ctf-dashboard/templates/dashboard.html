Module 00

Welcome to the OWASP Security Learning Platform

Learn, Break, Patch

The Motivation

This platform is designed specifically for students and developers with little to no prior exposure to cybersecurity or the covered OWASP security risks. The goal is to help you develop a security mindset for web applications by teaching you how to think like an attacker, and then showing you how to defend your code.

What is the OWASP Top 10 and what topics are covered?

“The OWASP Top 10 is a standard awareness document for developers and web application security. It represents a broad consensus about the most critical security risks to web applications.”

This learning platform focuses on two critical security risks from the 2025 OWASP Top 10 list:

A01: Broken Access Control

When an application fails to enforce boundaries, allowing users to view, modify, or delete data they shouldn't have access to.

A10: Mishandling of Exceptional Conditions

When unhandled or poorly handled system errors cause the system to become exploitable.

How the Platform Works

Each of the two Security Risk modules starts with a Learn section. Here, you will read a brief, straightforward breakdown of the security risk, how it occurs in the real world, and how to spot it.

It is important to note that the Learn section does not go into much theoretical depth. This platform was designed using the “Learn by Doing” mindset, specific vulnerabilities are showcased through the challenges you will work through.

After reading the Learn section, the platform offers a series of challenges. The challenges for each Security Risk live in two separate web apps. The source code for these apps is available in the repository inside the folder named after each Security Risk (for example, mishandling-exceptional-conditions). Don’t worry, these challenges are designed for beginners, with the goal of exposing you to a range of vulnerabilities under each Security Risk.

The Challenge Structure

Every challenge has two distinct stages:

The Break Stage (CTF)

CTF stands for “Capture the Flag.” In this phase, your goal is to actively exploit the web app’s vulnerability to achieve a certain goal (which will be set out for you). If you successfully execute the exploit, the system will hand you a secret “Flag” to prove your success. To check if your flag is correct, enter it in each challenge’s designated Flag text box.

The Patch Stage

Breaking things is only half the job. In this phase, you will dive into the backend code, locate the exact lines causing the vulnerability, and rewrite the logic to secure the application.

API Documentation (/docs)

For both vulnerable apps, this project offers a built-in /docs page (Swagger UI) where you can view all available API routes. This helps you send API requests to the server without setting up external tools like Postman.

When doing the challenges, try intercepting the API requests yourself first (using your browser's Developer Tools or a proxy) to see exactly what your browser is sending and what the server is returning, a vital skill in web security. If you get stuck or need to manipulate a payload easily, you can always fall back to the /docs page to see the API specifications and fire off requests from there.

How to explore source code

Because this project runs locally on your own machine, you have full access to the entire codebase. Technically, you could just open the files, search for the flags, and skip the exercises entirely. Please don't do that. You won't learn anything, and you'll rob yourself of the “aha!” moment when an exploit finally clicks.

To complete challenges, you will look through each web app’s source code, which can feel intimidating. That’s why each web app has a challenge-files folder containing what you need for both stages of each challenge. For the Patch stage, you will only ever need to modify code inside the challenge-files folder.

That doesn’t mean you can’t look through the other files. If you’re curious, feel free to explore how each web app is set up, just don’t use that as a shortcut to complete the challenges.

Take your time, break things, fix things, but most importantly, have fun!

Module 01 · OWASP A01

Broken Access Control

Authentication vs authorization

To understand Broken Access Control, we need to first look at two concepts that sound similar, but are actually completely different:

Authentication

Authentication refers to proving who you are, e.g. logging into your school’s student portal with your email and password.

Authorization

Authorization refers to proving what you are allowed to do, e.g. as a student, you are authorized to view your own grades but you’re not allowed to change them.

Broken Access Control is security risk that occurs when a web app successfully authenticates you, but fails to enforce proper authorization, allowing users to act outside of their intended permissions. In general, we can put Broken Access Control vulnerabilities into one of two buckets:

Vertical Privilege Escalation

A user gains access to a functionality that they are not permitted to access, e.g. a student reaches an admin page where they can drop other students from their courses.

Horizontal Privilege Escalation

A user gains access to resources belonging to another user that they shouldn’t have access to, e.g. a student can view another student’s academic transcript via the student portal.

How this shows up in code

Most cases of Broken Access Control (and all of the ones explored in these challenges) are caused by one of two vulnerabilities:

Broken Object Level Authorization (BOLA) & IDOR

The most common cause of horizontal escalation. Historically known as Insecure Direct Object Reference (IDOR), this occurs when an application provides direct access to a database object (like a file or a user profile) based on user-supplied input, such as an ID number in a URL. It becomes a BOLA vulnerability when the server takes that ID but fails to validate if the requesting user actually owns or is authorized to access that specific object.

Broken Function Level Authorization (BFLA)

The most common cause of vertical escalation. It occurs when an application relies on the client (like hiding a UI button) to restrict access to a feature, but the backend server fails to properly verify the user’s role before allowing them to execute that specific administrative function.

Module 02 · OWASP A10

Mishandling of Exceptional Conditions

Mishandling of Exceptional Conditions is a security risk that refers to any vulnerability where an application fails to properly handle exceptional (error) conditions. At its core, this vulnerability can happen in three main ways:

Failure to prevent an exceptional case

The application fails to anticipate and prevent edge cases, potentially causing the system to crash. e.g. A calculator app not sanitizing division by zero, causing the program to crash.

Failure to detect the issue

The application doesn’t recognize that something has gone wrong.

Failure to respond safely

The application detects an error but responds poorly (or not at all).

How this shows up in practice

The risk of Mishandling Exceptional Conditions can come in the form of many different vulnerabilities. The challenges for this topic will cover four of these vulnerabilities, namely:

Verbose error messages

When an error message gives away too much information.

Partial transactions

When multi-step operations fail mid-way.

Inconsistent error logic

When errors that are supposed to be the same are handled differently.
